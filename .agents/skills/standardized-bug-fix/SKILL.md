# 标准化问题修复流程

前置约束：

1. `AGENTS.md` §1 推断纪律与 §3 资金红线全程生效且优先级最高。
2. 本流程是 `/verified-dev` 在修 bug 场景下的细化，不替代它：
   阶段 0 红线自检、S1 至 S6 证据分级、Reference 清单一律照旧执行。
3. 代码文本按 `/quant-code-standards` §零 用美式英文。

适用场景：定位并修复缺陷、处理运行时异常、系统性排查。
不适用场景：纯格式调整、纯文档更新、新功能开发（走 `/verified-dev`）。

---

## 阶段 1：问题诊断

目标是定位根因，不是复现症状。

1. 收集事实：报错堆栈、`logs/` 下相关日志、复现步骤、影响的标的与时间窗。
2. 先复现再动手。不能稳定复现的问题，先补最小复现脚本放 `scripts/`；
   复现不了就如实说「无法复现」，不得凭猜测改代码。
3. 根因定位到具体文件与行号。写不出行号即表示尚未定位到。
4. 评估影响范围：是否影响已落地数据、是否影响历史回测结论、是否影响实盘下单行为。
   任一为「是」，则在修复计划中单列受污染产物清单与重生成方案。

产出 `research/notes/YYYYMMDD_issue_<name>.md`，内容含：现象、复现步骤、
根因（含行号）、影响范围、严重级（P0 立即修，P1 本轮修，P2 排期）。

P0 判据：会产生错误委托、会造成资金损失、会静默污染数据、会让历史结论失效。

---

## 阶段 2：修复规划

产出 `research/notes/YYYYMMDD_fixplan_<name>.md`，必须包含：

| 项 | 要求 |
|---|---|
| 修复方案 | 改哪个函数、改成什么、为什么这样改 |
| 备选方案 | 至少一个，并说明为何不选 |
| 依赖假设 | 按 S1 至 S6 标注证实来源；有未证实项即停下来问用户 |
| 影响面 | 受影响的调用方、配置、已落地数据、既有回测结果 |
| 回滚方案 | 精确到删哪几行或恢复哪个值，含依赖顺序 |
| 验收标准 | 先于修改写定，含至少一条有判别力的检验（见 `/verified-dev` §4.3） |

---

## 阶段 3：代码实施

1. 改动前备份或确认可用 `git diff` 回退。
2. 一次只修一个根因；顺手发现的其他问题登记到笔记，不夹带修改。
3. 遵守 `/quant-code-standards`；关键常量注明依据出处。
4. 语法自检：`python -m py_compile <file>`。

---

## 阶段 4：测试补充

1. 每个修复对应一个测试：`tests/test_fix_<id>_<name>.py`。
2. 测试必须先在修复前跑失败、修复后跑通过。只在修复后跑一次通过等于没有验证。
3. 边界用例必须覆盖：空数据、单元素、精度边界、跨时区边界、限频触发、部分成交。

---

## 阶段 5：质量验证

1. 全量测试：`pytest tests/ -q`。
2. 回归：确认既有产物未被意外改变，数据文件逐字节 `cmp`，回测结果逐笔对比。
3. 执行层专项：若改动触及 `*/execution/` 或风控闸，必须整表复查
   `/live-trading-risk-check`，不得只跑单元测试。
4. 判别力自问：如果这个修复是错的，上面哪一步会失败。答不上来即补检验。

---

## 阶段 6 与 7：文档与留痕

1. `WORKING_MEMORY.md` 更新「当前状态」与「未决项」，时间线追加一行，写明回滚要点。
2. 若修复改变了既有结论或数字：在对应的 `research/decisions/` 文件中并列修正前与修正后，
   并说明哪一份是权威口径。改变了结论方向或显著性的，须在摘要处即行标明。
3. 受污染的落地数据：列出清单，说明是重生成还是标记作废，不得不做说明地留着。

---

## 输出格式

```
## 修复报告

1. 根因（文件:行号，加一句话机制）
2. 修复方案（改了什么，为什么）
3. 测试（修复前失败与修复后通过的证据）
4. 回归结论（既有产物是否改变）
5. 受影响产物与处置
6. 回滚要点
7. 仍存疑事项
8. Reference（决策依据清单，强制置于最末）
```

## 红线（违反即判本轮修复无效）

1. 没复现就改代码。
2. 根因写不出行号却宣称已定位。
3. 测试只在修复后跑一次通过。
4. 修复夹带无关改动。
5. 改了执行层不复查风险表。
6. 数据或结论被污染却未列清单。
