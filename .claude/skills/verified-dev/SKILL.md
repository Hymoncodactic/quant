# 带交叉验证的代码开发流程

前置约束：

1. `CLAUDE.md` §1 推断纪律在本流程全程生效，优先级最高。
2. `CLAUDE.md` §3 资金红线高于一切，与本流程冲突时以红线为准。
3. 任何一步遇到未证实的假设，立即停下来向用户提问，不继续往下走。

必须严格按序执行五个阶段，禁止跳步。

---

## 阶段 0：红线自检（先于一切阶段，触线即判任务失败）

动手前逐条自问，任一条为「是」即停下来向用户确认：

| # | 自检项 | 依据 |
|:--:|---|---|
| 1 | 本次改动会产生真实委托、撤单、划转或出入金吗（只读接口不受限，写接口须用户当轮明确授权） | §3.1 |
| 2 | 本次改动会把 `DRY_RUN` 默认值改成 False，或绕过 `live: true` 断言吗 | §3.1 |
| 3 | 本次改动会把真实 API Key、Secret、Passphrase 写进代码、配置、日志、报告或任何会被展示的位置吗 | §3.2 |
| 4 | 本次改动会修改或删除 `data/*/raw/` 下的原始件吗 | §3.4 |
| 5 | 本次改动会引入非 ASCII 文件名或目录名吗（无例外） | §4.1 |
| 6 | 本次改动是否触及影响实盘下单行为的参数（阈值、仓位上限、频率上限、止损位、下单量精度、价格精度） | §1.4 |
| 7 | 本次改动是否跨场所复用了另一场所的口径、参数或结论（OKX 与 Trading 212 之间的费率、精度、交易时段、结算规则一律不通用） | §六 |
| 8 | 本次改动写入的代码文本是否全部为美式英文（标识符、注释、docstring、日志与异常消息） | §2.3 与 `/quant-code-standards` §零 |

| 9 | 本次改动是否会新建目录或新建文件（是则必须同步写 `README.md` 与模块头） | §4.3、§4.4 |

第 8、9 项为格式性约束，不需要用户裁定，但不满足即须在本阶段就地改正后再进入阶段 1。

---

## 阶段 1：读文档（写代码前必须完成）

### 1.1 定位：确定要改的代码文件与函数

按 `/quant-code-standards` §4.9 的五步定位流程执行：定层、定文件、定函数、查调用点、改。
产出「本次将要新增或修改的全部代码文件路径加具体函数名」。

任一步走不通（无法判断属于哪一层、文件没有功能索引、函数职责过重、调用点散落多处），
属结构缺陷而非搜索能力问题：记入最终输出的待改进项，并在动手前说明。

### 1.2 读说明文档（顺序固定，不可颠倒）

按以下顺序读，每一步读完再进下一步：

1. **待改文件所在目录的 `README.md`**（`CLAUDE.md` §4.3），再逐级向上读各级父目录的
   `README.md`，直到项目根。这一步先于读任何代码。
2. **待改文件的模块头 docstring**（§4.4），先于读函数体。
3. 项目根的 `CLAUDE.md`、`ARCHITECTURE.md`、`WORKING_MEMORY.md`。
4. 涉及数据的，读 `docs/data/<source>/DATA_SPEC.md`。

```bash
# Example: the file to be modified is crypto_trading/ingest/klines.py
# Read in this order:
#   crypto_trading/ingest/README.md
#   crypto_trading/README.md
#   README.md at the project root, plus CLAUDE.md / ARCHITECTURE.md / WORKING_MEMORY.md
#   the module docstring of crypto_trading/ingest/klines.py
#   docs/data/okx/DATA_SPEC.md when data is involved
```

用 `Read` 逐行读完，不得只 grep 关键词。

### 1.3 补齐缺失的说明文档（当场做，不推迟）

1. 某目录没有 `README.md`：**当场补齐**，按 `CLAUDE.md` §4.3 的六节结构写，
   逐个文件写明作用与存在必要性。补齐后再继续本流程，不允许标记为警告后跳过。
2. 某文件没有模块头，或模块头缺 §4.4 的任一节：**当场补齐**。
3. 补齐过程中发现某文件说不清存在必要性（无调用点、无产出、无人引用），
   按 `CLAUDE.md` §4.2 处置：删除，或在 `README.md` 中写明保留理由。

### 1.4 交叉比对（本阶段的核心，不可省略）

把文档描述的逻辑与代码实际实现逐条对照，产出一张表：

| 文档声称 | 代码实际（文件:行号） | 是否一致 |
|---|---|---|
| <文档中的一条陈述> | <对应代码位置与实际行为> | 一致 / 不一致 |

发现任何不一致即停下来问用户：是文档过时，还是代码有 bug。不得自行假定哪一方正确。

典型冲突场景：`DATA_SPEC.md` 写「K 线 timestamp 为开盘时刻」，而下载器按收盘时刻对齐。
二者只能有一个成立，且判断错误会让全部信号错位一根 bar。这类冲突必须由用户裁定。

## 阶段 2：确认关键假设（写代码前必须完成）

把本次改动依赖的全部假设列出，逐条标注证实来源（`CLAUDE.md` §1.1 的 S1 至 S6）：

| # | 假设 | 证实来源 | 是否已证实 |
|---|---|---|:---:|
| 1 | OKX K 线 ts 为该 bar 的开始时间，单位毫秒 | S4 官方文档 `GET /api/v5/market/candles` 字段表，加 S5 实证：相邻 ts 差恒等于 bar 周期 | 是 |
| 2 | Trading 212 账户结算币种为 GBP | S6 用户明言 | 是 |
| 3 | BTC-USDT 最小下单量 = 0.00001 | 仅凭记忆 | 否，须现调 `/api/v5/public/instruments` 取回 `minSz` |

只要有一条为「否」即停止，向用户提问或先取回权威事实，按 `CLAUDE.md` §1.2 的四要素
给出：推断是什么、依据与强度、如何证实、错了的后果。未落实前不写依赖它的代码。

### 2.1 交易所事实的取证规范（本项目特有，硬性）

凡涉及以下任一项，一律按 S4 现取，不得凭记忆：

| 类别 | 必须取回的字段 | 落地位置 |
|---|---|---|
| 合约与标的规格 | 最小下单量、下单量步进、价格精度、面值或合约乘数 | `data/reference/<venue>_instruments_<日期>.json` |
| 费率 | maker/taker 费率、当前费率档、印花税与 FX 费（T212） | `data/reference/<venue>_fees_<日期>.md` |
| 限频 | 各端点速率上限、封禁策略、重试建议 | 代码注释加 `<venue>/ingest/limits.py` |
| 时间口径 | 时间戳单位（秒或毫秒）、时区、bar 对齐方式 | `DATA_SPEC.md` |
| 交易时段与结算 | 开收盘时间、假期、T+N、隔夜费 | `data/reference/` |

取回后在 Reference 清单中给出文档 URL 加章节标题，或接口路径加实际返回片段。

## 阶段 3：写代码

0. 动手前已按阶段 1.2 读完所在目录 `README.md` 与本文件模块头，未读不得开写。
1. 与周边代码风格一致，遵守 `/quant-code-standards`（含 §零 语言：代码文本一律美式英文）。
2. 关键常量注明依据出处（哪个配置、哪行源码、哪个官方文档、哪个接口返回），不留裸数字。
3. 涉及金额、数量、价格的计算，显式写明单位与精度，并在函数 docstring 中声明。
4. 涉及外部 API 的调用，按 `/quant-error-handling` 包好重试、限频、超时与幂等。

---

## 阶段 4：验证（三层，缺一不可）

### 4.1 跑通

执行并确认无报错。跑通只是最低门槛，不能作为逻辑正确的证据。

### 4.2 逻辑正确性校验：三类来源，满足任一条即可

| 类型 | 做法 | 本项目举例 |
|---|---|---|
| A 本地 md 比对 | 与说明文档记载的逻辑或取值逐条核对 | `DATA_SPEC.md` 的字段口径表 |
| B 本地数据比对 | 用实际数据做可复现的量化检验 | 下载的日线满足 `high >= max(open,close) >= min(open,close) >= low` 全量成立；日线由小时线聚合后与直接下载的日线逐位一致 |
| C 官方或权威源比对 | 交易所官方文档、接口返回、券商对账单 | 用账户历史成交对账单核对手续费计算函数 |

三选一即可，不必三条都做。但选定的那一条必须落到实处，能指出具体文件、行号、数值或
接口路径，不能是「看起来应该是这样」。

### 4.3 判别力检查（对 4.2 所选检验的质量要求，不是额外一轮验证）

无论用 A、B、C 哪一种，都要能回答：如果实现是错的，这个检验会不会失败。

示例一：验证「下单量向下取整到步进」时，若取的样本量恰好都是步进的整数倍，
无论实现对错都会通过，等于没有验证，必须选带余数的样本。
示例二：验证时区处理时选一个不跨日的样本没有判别力，必须选跨 UTC 零点的样本。

答案若是「不会失败」，则更换样本或更换检验方式，不得据此宣称验证通过。

## 阶段 5：留痕

按 `CLAUDE.md` §五 更新 `WORKING_MEMORY.md`：

1. 当前状态：刷新本次改动后的模块状态。
2. 未决项：新增或消解的未决问题。
3. 时间线：追加一行，含时刻、动作、回滚要点。只增不改；结论变了写新行注明
   「原值改为现值，加依据」，不删旧行。

4. 工作区清理：按 `CLAUDE.md` §4.2 处置本轮产生的全部过程件，只保留最小产出集，
   纯过渡文件与未完成的产出件一律删除，并列出去向清单。
5. 目录说明核对：本轮改动过的每个目录，逐个复核其 `README.md` 的文件清单、职责表述、
   产出与清理约定是否与现状一致，不一致即改（`CLAUDE.md` §4.3）。
6. 模块头核对与精简：本轮改动过的每个源文件，核对模块头六节与实现是否一致，
   在 Change log 追加一行；同时判断可否精简——无调用点的函数、无人使用的参数、
   重复实现的逻辑一律删除，删除结果写进 Change log（`CLAUDE.md` §4.4）。

回滚要点写清三件事：改了哪个函数、改了什么、怎么退回去。若依赖其他改动，注明顺序。

示例时间线行：

```
| 2026-08-19 14:20 | 修正 crypto_trading/ingest/klines.py 的 bar 时间戳对齐：
  fetch_candles() 的 ts 由收盘时刻改为开盘时刻，新增常量 BAR_TS_IS_OPEN。
  回滚：改回 ts + period_ms；注意已落地的 curated 数据需一并重生成，
  否则新旧混存会错位一根 bar |
```

代码本身的逐行变更由 git 承担，本文件只记为什么改与怎么退回去，这两样 git diff 不体现。

## 文档与语言口径

1. 技术文档按 `CLAUDE.md` §2.1.2 与 §2.2：面向机器读者、无装饰性符号、无第二人称、
   不引用交互过程、无 AI 署名。`research/notes/` 下的个人随笔与 `WORKING_MEMORY.md`
   不受此约束。
2. 语言按 `CLAUDE.md` §2.3：md 文档用中文；代码及代码内的注释、docstring、日志与
   异常消息一律美式英文。

## 最终输出格式

完成后必须给出：

1. 红线自检结论：阶段 0 的八条逐条给出「否」或「是（已获授权，附授权原话）」。
2. 已读文档清单，含缺 md 的目录警告。
3. 文档与代码交叉比对表，含不一致项及其裁定结果。
4. 假设清单：每条的证实来源；曾停下来问过什么；交易所事实的取证落地位置。
5. 验证结果：跑通结果、所用的 A/B/C 比对、判别力说明。
6. `WORKING_MEMORY.md` 已更新的条目（状态、未决项、时间线那一行）。
7. 本轮新建文件清单及其去向（`CLAUDE.md` §4.2 第 9 条），每项标注「保留（登记位置）」
   或「已删除」；未新建文件时写明该事实。
8. 本轮改动过的目录清单，逐个标注其 `README.md` 的核对结果（已同步 / 已补齐 / 无需改）。
9. 本轮改动过的源文件清单，逐个标注模块头核对结果与精简结果（删了哪些函数或参数）。
10. 仍未证实或仍存疑的事项，逐条列出，每条按 `CLAUDE.md` §1.5 附本方推荐做法；
    可自行判定的不得列入本项，应当已经处置并在正文交代。
11. Reference 决策依据清单，强制放在输出最末尾。

### Reference 清单格式（强制）

每一个决策与结论都要能追溯到一个具体来源。禁止「根据文档」「根据代码」「根据 OKX 文档」
这类不指名的表述。

```markdown
## Reference（决策依据清单）

| # | 决策 / 结论 | 依据类型 | 具体来源（精确到文件:行号 / 数值 / 接口路径 / 文档 URL 与章节） |
|---|---|---|---|
| 1 | BTC-USDT 下单量步进 = 0.00000001 | C 官方权威 | `GET /api/v5/public/instruments?instType=SPOT` 返回 `{"instId":"BTC-USDT","lotSz":"0.00000001","minSz":"0.00001"}`，取回时间 2026-08-19，存于 `data/reference/okx_instruments_20260819.json` |
| 2 | K 线 ts 单位为毫秒且为开盘时刻 | B 本地数据 | `data/okx/raw/BTC-USDT/1h/year=2026/20260801.parquet` 实测相邻 ts 差恒为 3600000 |
| 3 | 账户计价币种 GBP | S6 用户明言 | 用户 2026-08-19 消息：「trading212 里面我存放的是英镑」 |
| 4 | 某项待定结论 | 无 | 未证实，已向用户提问，待答复 |
```

依据类型统一标注 A（本地 md、代码、配置）、B（本地数据）、C（官方权威源）。
没有来源的决策必须显式标注「未证实」，不允许省略不写。

## 红线（违反即视为本次任务失败）

1. 触发了阶段 0 任一条红线却没有停下来确认。
2. 凭模型记忆写出交易所 API 的字段、单位、精度、费率、限频，未按 S4 取证。
3. 没读完文档就动手写代码。
4. 把反推包装成「已校验」或「已验证」。
5. 遇到未证实假设不提问，自行猜测继续。
6. 只报「跑通了」就宣称完成。
7. 用无判别力的检验宣称验证通过。
8. 改了代码不更新 `WORKING_MEMORY.md`，尤其是回滚要点。
9. 把过程件、调试脚本、临时输出留在项目目录内不作处置（`CLAUDE.md` §4.2）。
10. 未读所在目录 `README.md` 与模块头就动手改代码（`CLAUDE.md` §4.3、§4.4）。
11. 新建目录或新建文件后不写 `README.md` 与模块头。
12. 留下未完成的产出件，或留下多份等价的中间产物。
13. 把可自行判定的事项包装成「需用户裁定」抛回给用户，或请示时不带推荐做法
    （`CLAUDE.md` §1.5）。
