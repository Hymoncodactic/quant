# 带交叉验证的代码开发流程

> 前置：`CLAUDE.md` §1 的**推断纪律**在本流程全程生效且优先级最高；
> `CLAUDE.md` §3 的**资金红线**高于一切，与本流程冲突时以红线为准。
> **任何一步遇到未证实的假设，立即停下来问用户，不要往下走。**

必须**严格按序**执行五个阶段，禁止跳步。

---

## 阶段 0：红线自检（先于一切阶段，踩线=任务失败）

动手前逐条自问，任一条为「是」即停下来向用户确认：

1. ⛔ 本次改动会**产生真实委托/撤单/划转/出入金**吗？（`CLAUDE.md` §3.1）
   —— 只读接口不受限；任何写接口须用户当轮明确授权。
2. ⛔ 本次改动会把 `DRY_RUN` 默认值改成 False，或绕过 `live: true` 断言吗？
3. ⛔ 本次改动会把真实 API Key / Secret / Passphrase 写进代码、配置、日志、
   报告或任何会被展示的位置吗？（§3.2）
4. ⛔ 本次改动会修改或删除 `data/*/raw/` 下的原始件吗？（§3.4）
5. ⛔ 本次改动会引入非 ASCII 文件名或目录名吗？（`CLAUDE.md` §4.1，无例外）
6. ⚠️ 本次改动是否触及**影响实盘下单行为的参数**（阈值、仓位上限、频率上限、
   止损位、下单量精度、价格精度）？是则按 `CLAUDE.md` §1.4 先问用户。
7. ⚠️ 本次改动是否跨场所复用了另一场所的口径/参数/结论？
   （OKX ↔ Trading 212 之间的费率、精度、交易时段、结算规则一律不通用。）

## 阶段 1：读文档（写代码前必须完成）

### 1.1 定位：确定要改的代码文件与函数

按 `/quant-code-standards` §4.9 的五步定位流程走：**定层 → 定文件 → 定函数 →
查调用点 → 改**。产出「本次将要新增或修改的全部代码文件路径 + 具体函数名」。

任一步走不通（猜不到在哪层、文件没有功能索引、函数职责过重、调用点散落多处），
不是搜索能力问题，是结构缺陷——记入最终输出的待改进项，并在动手前说明。

### 1.2 自动发现说明文档

对每个待改文件，收集**它所在目录 + 各级父目录（直到项目根）下的全部 `*.md`**。

```bash
# 示例：待改 crypto_trading/ingest/klines.py
# 需读取：
#   crypto_trading/ingest/*.md
#   crypto_trading/*.md
#   *.md                       ← 含 CLAUDE.md、ARCHITECTURE.md、WORKING_MEMORY.md
# 另：涉及数据的，须读对应 data/<venue>/curated/*/DATA_SPEC.md
```

用 `Read` **逐行读完**，不得只 grep 关键词。

### 1.3 记录缺失文档

某目录没有 `.md` 说明 → **记为警告并在最终输出中列出**（目标是「所有数据目录与
模块目录都配备 md 说明」），但**不阻塞**流程。

### 1.4 交叉比对（本阶段的核心，不可省略）

把文档描述的逻辑与**代码实际实现**逐条对照，产出一张表：

| 文档声称 | 代码实际（文件:行号） | 一致? |
|---|---|---|
| … | … | 一致 / 不一致 |

**发现任何不一致 → 停下来问用户**：是文档过时，还是代码有 bug？**不要自行假定哪个对。**

> 典型冲突场景：`DATA_SPEC.md` 写「K 线 timestamp 为开盘时刻」，而下载器按收盘时刻
> 对齐。二者只能有一个对，且错了会让全部信号错位一根 bar。这类冲突必须由用户裁定。

## 阶段 2：确认关键假设（写代码前必须完成）

把本次改动依赖的**全部假设**列出，逐条标注证实来源（`CLAUDE.md` §1.1 的 S1–S6）：

| # | 假设 | 证实来源 | 已证实? |
|---|---|---|:---:|
| 1 | OKX K 线 ts 为该 bar 的**开始**时间，毫秒 | S4 官方文档 `GET /api/v5/market/candles` 字段表 + S5 实证：相邻 ts 差恒等于 bar 周期 | 是 |
| 2 | Trading 212 账户结算币种为 GBP | S6 用户明言 | 是 |
| 3 | BTC-USDT 最小下单量 = 0.00001 | 仅凭记忆 | 否 **须现调 `/api/v5/public/instruments` 取回 `minSz`** |

**只要有一条为「否」→ 停止，向用户提问或先取回权威事实**（按 `CLAUDE.md` §1.2
的四要素：推断是什么 / 依据与强度 / 如何证实 / 错了的后果）。**未落实前不写依赖它的代码。**

### 2.1 交易所事实的取证规范（本项目特有，硬性）

凡涉及以下任一项，一律按 S4 现取，不得凭记忆：

| 类别 | 必须取回的字段 | 落地位置 |
|---|---|---|
| 合约/标的规格 | 最小下单量、下单量步进、价格精度、面值/合约乘数 | `data/reference/<venue>_instruments_<日期>.json` |
| 费率 | maker/taker 费率、当前费率档、印花税/FX 费（T212） | `data/reference/<venue>_fees_<日期>.md` |
| 限频 | 各端点速率上限、封禁策略、重试建议 | 代码注释 + `<venue>/ingest/limits.py` |
| 时间口径 | 时间戳单位（秒/毫秒）、时区、bar 对齐方式 | `DATA_SPEC.md` |
| 交易时段/结算 | 开收盘时间、假期、T+N、隔夜费 | `data/reference/` |

取回后在 Reference 清单中给出**文档 URL + 章节标题**或**接口路径 + 实际返回片段**。

## 阶段 3：写代码

- 与周边代码风格一致，遵守 `/quant-code-standards`
- 关键常量注明**依据出处**（哪个配置/哪行源码/哪个官方文档/哪个接口返回），不留裸数字
- 涉及金额、数量、价格的计算，显式写明单位与精度，并在函数 docstring 中声明
- 涉及外部 API 的调用，按 `/quant-error-handling` 包好重试、限频、超时与幂等

---

## 阶段 4：验证（三层，缺一不可）

### 4.1 跑通

执行并确认无报错。**跑通只是最低门槛，不能作为「逻辑正确」的证据。**

### 4.2 逻辑正确性校验 —— 三类来源，**满足任一条即可**

| 类型 | 做法 | 本项目举例 |
|---|---|---|
| **A. 本地 md 比对** | 与说明文档记载的逻辑/取值逐条核对 | `DATA_SPEC.md` 的字段口径表 |
| **B. 本地数据比对** | 用实际数据做可复现的量化检验 | 下载的日线 `high >= max(open,close) >= min(open,close) >= low` 全量成立；日线聚合自小时线后与直接下载的日线逐位一致 |
| **C. 官方/权威源比对** | 交易所官方文档、接口返回、券商对账单 | 用账户历史成交对账单核对手续费计算函数 |

**三选一即可，不必三条都做。** 但选定的那一条必须**真正落到实处**（能指出具体
文件/行号/数值/接口路径），不能是「看起来应该是这样」。

### 4.3 判别力检查（对 4.2 所选检验的质量要求，不是额外一轮验证）

无论用 A/B/C 哪一种，都要能回答一句：**「如果我的实现是错的，这个检验会不会失败？」**

> 举例：验证「下单量向下取整到步进」时，若取的样本量恰好都是步进的整数倍，
> 无论实现对错都会「通过」，等于没验；必须选带余数的样本。
> 同理，验证时区处理时选一个**不跨日**的样本没有判别力，必须选跨 UTC 零点的样本。

答案若是「不会失败」→ **换样本或换检验方式**，不得据此宣称验证通过。

## 阶段 5：留痕

按 `CLAUDE.md` §五 更新 `WORKING_MEMORY.md`：

1. **当前状态** —— 刷新本次改动后的模块状态。
2. **未决项** —— 新增或消解的未决问题。
3. **时间线** —— 追加一行：时刻 + 动作 + **回滚要点**。只增不改；
   结论变了写新行注明「原值 → 现值 + 依据」，不删旧行。

回滚要点写清三件事：**改了哪个函数**、**改了什么**、**怎么退回去**
（若依赖其他改动，注明顺序）。

示例时间线行：
```
| 2026-08-19 14:20 | 修正 crypto_trading/ingest/klines.py 的 bar 时间戳对齐：
  fetch_candles() 的 ts 由收盘时刻改为开盘时刻，新增常量 BAR_TS_IS_OPEN。
  回滚：改回 ts + period_ms；注意已落地的 curated 数据需一并重生成，
  否则新旧混存会错位一根 bar |
```

代码本身的逐行变更由 git 承担（若已 `git init`），本文件只记**为什么改**与
**怎么退回去**——这两样 git diff 看不出来。

## 文档客观性

本项目产出的技术文档（说明文档、方法论、裁定、报告）按 `CLAUDE.md` §2.1.2 与 §2.2：
面向机器读者、无装饰性符号、无第二人称、不引用交互过程、无 AI 署名。
`research/notes/` 下的个人随笔与 `WORKING_MEMORY.md` 不受此约束。

## 最终输出格式

完成后**必须**给出：

1. **红线自检结论**（阶段 0 七条逐条给出「否/是（已获授权，授权原话）」）
2. **已读文档清单**（含缺 md 的目录警告）
3. **文档 vs 代码交叉比对表**（不一致项及其裁定结果）
4. **假设清单**（每条的证实来源；曾停下来问过什么；交易所事实的取证落地位置）
5. **验证结果**（跑通结果 + 所用的 A/B/C 比对 + 判别力说明）
6. **WORKING_MEMORY.md 已更新的条目**（状态 / 未决项 / 时间线那一行）
7. **仍未证实 / 仍存疑的事项**（明确列出，不藏着）
8. **Reference（决策依据清单）** ← **强制，放在输出最末尾**

### Reference 清单格式（强制）

**每一个决策/结论都要能追溯到一个具体来源。** 禁止写「根据文档」「根据代码」
「根据 OKX 文档」这类不指名的表述。

```markdown
## Reference（决策依据清单）

| # | 决策 / 结论 | 依据类型 | 具体来源（精确到文件:行号 / 数值 / 接口路径 / 文档 URL 与章节） |
|---|---|---|---|
| 1 | BTC-USDT 下单量步进 = 0.00000001 | C 官方权威 | `GET /api/v5/public/instruments?instType=SPOT` 返回 `{"instId":"BTC-USDT","lotSz":"0.00000001","minSz":"0.00001"}`，取回时间 2026-08-19，存于 `data/reference/okx_instruments_20260819.json` |
| 2 | K 线 ts 单位为毫秒且为开盘时刻 | B 本地数据 | `data/okx/raw/BTC-USDT/1h/year=2026/20260801.parquet` 实测相邻 ts 差恒为 3600000 |
| 3 | 账户计价币种 GBP | S6 用户明言 | 用户 2026-08-19 消息：「trading212里面我存放的是英镑」 |
| 4 | ~~xxx~~ | **无** | ⚠️ **未证实，已向用户提问，待答复** |
```

- 依据类型统一标注 **A（本地 md/代码/配置）/ B（本地数据）/ C（官方权威源）**
- **没有来源的决策必须显式标 ⚠️ 未证实**，不允许省略不写

## 红线（违反即视为本次任务失败）

- ❌ 触发了阶段 0 任一条红线却没有停下来确认
- ❌ 凭模型记忆写出交易所 API 的字段/单位/精度/费率/限频，未按 S4 取证
- ❌ 没读完文档就动手写代码
- ❌ 把反推包装成「已校验」「已验证」
- ❌ 遇到未证实假设不问、自行猜测继续
- ❌ 只报「跑通了」就宣称完成
- ❌ 用**无判别力**的检验宣称验证通过
- ❌ 改了代码不更新 WORKING_MEMORY.md（尤其是回滚要点）
